# Layer B: English written into the shipped files

Layer B means editing a **copy** of a game's data so no plugin is needed. Keep the
originals: work in `<game>.en/` or keep `.wl-bak-*` copies, same rule as Layer A.
Nothing here is automated yet. This page is the plan and a plain statement of what
each engine needs. `wl-scan` tells you which engine each of your games uses.

The translation call is the same for every engine:
`GET http://127.0.0.1:8765/translate?from=ja&to=en&text=…` (see the README's
"Translation endpoint" section).

| Engine | Where the text usually is | Free CLI, end to end? | Catch |
|---|---|---|---|
| RPG Maker MV / MZ | `data/*.json` or `www/data/*.json`: Map, CommonEvents, Actors, Items, System… | **Yes.** Plain JSON; a short Python walker over event codes 101/401/102/402/405 plus database names. No outside tool. | Some builds pack `data/` into `package.nw` or the exe; unpack first. Word wrap needs a line-length pass. |
| Electron / NW.js | `resources/app.asar`, `resources/app/`, or `package.nw` | **Yes.** `npx @electron/asar extract` / `pack` when packed; plain files otherwise. | Newer Electron may enforce asar integrity (a fuse) and reject a modified asar. Strings may sit inside minified JS. |
| Godot | `.pck` (separate or embedded in the exe): `.csv`/`.translation`/`.tres`, or compiled GDScript | **Mostly.** GDRE Tools (gdsdecomp, headless) to recover; godotpcktool to unpack/repack. | Encrypted `.pck` needs the key (gdke can pull it from the exe). Text inside compiled scripts must be decompiled and repacked as source, per title. |
| Flash projector | SWF appended to the exe: DefineEditText / DefineText, ActionScript strings | **Partly.** JPEXS FFDec has a CLI (`-export text`, `-importText`); needs Java. | Static text uses embedded font subsets that often lack Latin glyphs, so English can render blank until a font is swapped. Text drawn as shapes or bitmaps can't be edited this way. |
| WolfRPG | `.wolf` archives / `Data/` | **Yes, with Windows CLI tools under Wine**: UberWolf/WolfDec to decrypt, WolfTL to dump/patch. | The newest Wolf encryption versions lag behind the tools. |
| Unity (Mono / IL2CPP) | serialized assets / MonoBehaviour fields / TextAssets | **Not promised.** | See below. Layer A is the answer for Unity. |
| Packed single exe (e.g. Enigma Virtual Box) | inside the exe | Unpack first (EnigmaVBUnpacker, a Windows tool, under Wine), then treat by engine. | `wl-scan` reports "unknown" when it finds no engine markers. |

**Paid tools:** none are required. GUI-only conveniences exist (Translator++ for RPG
Maker, UABEA for Unity assets), but nothing above depends on them.

## Why Unity stays on Layer A

In some Unity titles, known dialogue lines aren't in the files as UTF-8 or UTF-16, and
asset string dumps are noise. The text is serialized inside custom MonoBehaviours,
compressed bundles, or built at runtime. Field-level extraction would need:

1. Type trees for the game's own classes. For Mono, generate them from
   `<Game>_Data/Managed/Assembly-CSharp.dll` (TypeTreeGenerator / UnityPy's typetree
   support). For IL2CPP, first produce dummy assemblies with Cpp2IL or Il2CppDumper from
   `GameAssembly.dll` + `global-metadata.dat`, then generate type trees from those.
2. UnityPy reads the MonoBehaviours with those trees, swaps strings, writes the bundle
   back, then the game is tested per title (bundle CRCs, Addressables catalogs).

That is per-title engineering, not a bulk job. The runtime hook already shows English
and caches every line to `BepInEx/Translation/en/Text/_AutoGeneratedTranslations.txt`,
which can be hand-edited and takes precedence over live requests.

## Suggested order

1. RPG Maker MV/MZ JSON (pure Python, no outside tools).
2. Electron / NW.js.
3. Godot pck.
4. Flash, only if the font problem allows it.
